# DSH 秘书与判局层 · 第一阶段 MVP PRD

> 日期：2026-11-22。依据：NEW-REPO-BRIEF §5–§12（已裁事项）、01-ORIGIN-AND-EVOLUTION、02-DSH-EXTENSION-MAP-rc5，以及 2026-11-22 老板与 Claude Code 的对齐对话（本文第 1–2 章中标「对话定」的条目）。
> 状态：PRD 草案，新仓未建。冲突时以简报的已裁事项为准；本文只收窄范围和排序，不推翻已裁事项。

## 1. 背景与目标

**长期定位**：开源产品，面向所有用户。在 DeepSeek Harness（DSH）官方骨架上提供三样东西：
- 一个永远接得住话、**永不亲自执行**的秘书，作为单一入口；
- 一套人人可沉淀、可评测的判局层（gate）；
- 一套让秘书有连续性和真实感的记忆。

**开发策略**（对话定）：
- 先做到老板自己满意，再找用户。格式按「别人能装」设计，功能优先级按老板自用排。
- 单线推进，最小 MVP，每一步都可用，在可用状态上迭代。设计包里的大量调研是储备，用到时再取，不构成待办。
- 以官方为骨架：编排交给官方 agent-team，不自建编排。

**第一阶段目标**：一个装在本机 DSH 桌面客户端里的插件，跑通这样一个闭环：
1. 老板只和秘书对话；
2. 秘书把活派给一个工作区；
3. 工作区（Lead）按需拉起官方 team 执行；
4. gate 在关键节点拦住不合格的动作；
5. 全过程落进事件日志；
6. 需要老板拍板的事以「一句话 + 选项」送到面前。

**为什么现在做**：DSH 源码实读（02 号文件）确认了三件事都可行：官方给插件留有可拦截的工具前置钩子、插件可以跨会话派活、主区域可以注入面板。这是第一阶段的技术前提。

## 2. 最终交付结果

一个 npm 包形态的 DSH 插件，包含后端（主线）与前端（支线）。

### 2.1 后端（主线）

| 组件 | 交付内容 |
|---|---|
| 秘书 | 专用 agent preset，**零执行工具**：预设只装配自研工具，再用 agent 作用域 `tools.restrict({allow})` 兜底。秘书对老板的全部输出必须经过三个结构化说话工具（对话定）：**说一句**（一句话 + 表情标签）、**问一件事**（一句话 + ≤3 个选项，选项带后果说明和推荐标记，并标明可否附言）、**递一份文件**（结论 / 理由 / 影响三段 + 证据链接）。她的自由文本只留在原生会话里（L3） |
| 派发 | 秘书的派活和查状态工具：通过 `sessionController.create({cwd, agentPreset})` 建工作区根会话，用 `session.prompt` 投递任务，用 `observeProjections/observeEvent` 读状态。第一阶段只支持**一个工作区** |
| 工作区 | 工作区主会话兼任 Lead，按需启用官方 agent-team 或派 solo worker。照搬 louifinn 纪律：先落库再投递、Lead 只有提议权、项目并发上限 |
| 待裁队列 | 统一收集三类需要老板的事：gate 上报、秘书主动提问、**DSH 权限审批请求（ask）**。权限审批必须汇入这个队列，否则默认界面不显示原生会话，任务会卡死（对话定）。一次只呈现一件 |
| 判局层 | 最小注册表：条目带 id、插入点、判据、版本、红绿 fixture 指针。所有硬闸都通过 `tools/pre-execute` 返回 deny 并附理由。首批 2–3 个 gate：① **completion.verify-rerun**：宣布完成时，验证命令必须由独立方重跑通过；② **dispatch.changed-paths**：观察面取会话 diffs 与 git 脏路径的并集，会话里出现 shell 写入或 str_replace_editor 时判 `unmeasured`，不放行；③（可选）contract 类，任务缺验收标准时拒绝创建 |
| 事件日志 | 追加式 JSONL，把 DSH 的 `session/event`、`tools/result`、`team/task`、`agent/status`、`subagent/*` 归一化，再加上 gate 判定和秘书说话事件。它就是 M0 的雏形，前端和所有读数都只从这里投影 |
| 记忆（最简） | Markdown 实体页 + git，唯一写入者。第一阶段只记老板的**纠正、偏好、否决**，每条带出处（事件日志引用）。秘书开新会话时注入 |

### 2.2 前端（支线，对话定）

像素前端是 DSH 客户端的**默认主页面**。DSH 原生界面（左侧 session 列表 + 中间会话）只在第三层出现。

| 层级 | 呈现 |
|---|---|
| ① 房间 | 一间等距 2:1 剖面办公室：秘书坐门口前台，Lead 坐主位；团队拉起时 worker 走进房间坐到工位上，解散时离开。屏幕光代表四种状态：工作中、卡住、待裁、完成。gate 拦截时有可见的拦截动作。完成类事件只改变小人状态，不进对话 |
| ② NPC 对话 | 左侧放大的秘书立绘（表情由确定性映射表决定），底部对话框显示一句话（约 40 字以内）+ 选项 + 附言输入 + 剩余待办计数，另有一个历史回看按钮。对话框是与秘书对话的**唯一主界面**，只和秘书说话；点其他 NPC 只弹卡片 |
| ③ 文件 | 秘书「递过来」的纸张浮层：结论 / 理由 / 影响 |
| ④ 卡片 | 点击小人弹出：当前任务、最近的 gate 判定、证据摘要 |
| ⑤ 原生 | 一键深链到任一会话（含秘书自己）的 DSH 原生界面；返回后恢复像素主页 |

画风：温暖的剖面办公室，原生分辨率像素，色板冻结（32–48 色），物体加深色描边。环境低饱和，**只有状态信号使用高饱和色**。小人行为由确定性映射表决定，不让 LLM 实时决定。

## 3. 技术栈

| 层 | 选型 | 依据 |
|---|---|---|
| 宿主 | DSH **0.2.2-rc.5**，桌面端从 rc.3 升级到 rc.5 | 插件构建版本不满足宿主版本即被禁用（`plugin-compatibility.ts`） |
| 插件 | TypeScript，Cordis 函数式插件，在 profile 级 patch 中插入一行，不改官方行 | 02 号文件 §1 |
| 拦截 | `tools/pre-execute`（prepend）+ `tools.guard()` 同步兜底 | 唯一可事前否决、并把理由回给模型的口子 |
| 跨会话 | `ctx.sessionController.*` | 进程内调用不受远程访问策略拦截 |
| 存储 | `ctx.storageDomain`（工作区映射、待裁队列）；事件日志用 JSONL 文件；记忆用 Markdown + git | 只有两类真相：注册表管定义，日志族管发生了什么 |
| 前端 | 插件 client 半区（`dsh.client` + `./client`），注入 `main` keyed 插槽，侧栏默认收起；数据走自研 `@Remote({mode:'stream'})` | 宿主事件转发是白名单，不可扩展 |
| 渲染 | Canvas 2D 游戏引擎，**待样张验证后选定**（Phaser 3 或 PixiJS） | 老板明确旧仓实现不作参考，不预设结论 |
| 素材 | 单一 AI 生图来源 + 冻结色板 + 规格检查 | 混用来源会导致观感不一致（旧仓需求 §33.8） |

## 4. 分阶段执行步骤

单线推进，每个阶段结束时都必须是一个可安装、可用的状态。前端作为支线，在后端阶段的间隙推进，不阻塞主线。

### 阶段 0：验证 spike（不写产品代码）
1. 桌面端升级到 rc.5，确认插件安装和启用链路。
2. 最小插件实测：`tools/pre-execute` 对 `team_task_update(complete)` 返回 deny，模型能收到理由并据此调整。
3. 零工具 preset：用 `tools.view` 打出秘书会话的实际工具清单，确认没有任何执行类工具。
4. `sessionController.create({cwd})` + `session.prompt` 跨会话派活实测。
5. 前端：插件能否指定默认主面板、能否控制侧栏收起和展开。
6. 权限审批（ask）能否被插件截获并转入自建队列。

### 阶段 1：架构与开发规范 + 骨架
1. 写开发规范，专门针对旧仓的病根：注释和自检脚本要有比例上限；gate 不注册就不存在；每个判据必须带红绿双向 fixture；状态只有两类真相；派生态永不回写。
2. 写事件日志 schema v0：只覆盖第一阶段用到的 kind，字段对照 DSH 原生事件。
3. 插件骨架：preset、工具注册、事件归一化落盘。

### 阶段 2：秘书与派发
秘书 preset、三个说话工具、派发和查状态工具、工作区注册（单个）、待裁队列（含权限审批）。

### 阶段 3：判局层
最小注册表，以及 verify-rerun、changed-paths（含 unmeasured）两个 gate。每次判定都写进事件日志，并建一个人工标注台账，记录每次拦截判得对不对。

### 阶段 4：最简记忆
实体页 + git，唯一写入者；只记纠正、偏好、否决；带出处；新会话注入。

### 阶段 5：真实闭环狗粮
在老板的一个真实项目上，跑至少一周真实任务，收集摩擦、拦截台账和打扰次数。

### 前端支线
1. **F1 风格样张**：一间房 + 三个小人 + 三种状态 + 立绘一张，交老板过目。不通过就不进 F2。
2. **F2 房间投影**：由事件日志驱动，实现人员进出和四种状态。
3. **F3 NPC 对话**：立绘、对话框、选项、附言、历史回看，接秘书说话工具和待裁队列。
4. **F4 卡片 + 文件浮层 + L3 深链**，以及主页与原生界面的往返。

## 5. 验证方式

| 对象 | 验证 |
|---|---|
| 阶段 0 各 spike | 在本机 rc.5 实跑，留命令和输出；结论按「确证 / 不成立」记录，不成立的项回写本 PRD |
| 零执行秘书 | 工具清单实测截图 + 一次「让秘书自己改代码」的诱导测试，她必须派活而不是执行 |
| gate | 每个判据都有红绿双向 fixture：去掉判据就变红；变异测试证明判据有区分力；在真实会话里各触发一次拦截和一次放行 |
| changed-paths 盲区 | 构造一个用 shell 写文件的任务，必须判 `unmeasured` 而不是 ok |
| 待裁队列 | 构造一次权限审批，必须出现在对话框选项里，选择后能让原会话继续执行 |
| 事件日志 | 前端和读数只从日志投影；删掉派生状态后能从日志重建 |
| 记忆 | 纠正一条偏好后，开新会话，秘书不再重复问 |
| 前端 | 老板过目样张；投影与事件日志一一对应，点击小人能回溯到具体事件 |
| 闭环 | 阶段 5 一周狗粮：拦截台账、打扰次数、重复提问次数有真实读数 |

所有「完成」都需要独立证据，不能自报。

## 6. 自检标准

- [ ] 秘书工具清单中没有任何执行类工具（实测，不是看配置）
- [ ] 秘书对老板的输出 100% 经过三个说话工具；单句长度和选项数超限即被拒
- [ ] 每个 gate 有注册条目、版本号、红绿 fixture，且都走 pre-execute
- [ ] 没测到的情况判 `unmeasured`，从不冒充 ok
- [ ] 系统中只有两类真相；前端和读数没有任何回写路径
- [ ] 权限审批不会因为默认界面不显示原生会话而被遗漏
- [ ] 每个阶段结束时插件都可安装、可用
- [ ] 注释和自检代码的比例在开发规范的上限内

## 7. 风险与应对

| 风险 | 应对 |
|---|---|
| DSH 为 rc 版本、API 不稳定，工具名和 action 枚举可能漂移 | 钉版本；工具名集中在一处定义；每次升级走兼容审计并重跑全部 fixture |
| 预设不是安全边界，升级后宿主可能新增全局工具 | preset 与 allow 白名单双保险；升级审计必须重新检查秘书的实测工具清单 |
| shell 写入不可见，changed-paths 有盲区 | 观察面取并集，有盲区时判 unmeasured；接受第一阶段这个 gate 拦截率偏高，用人工标注台账校准 |
| 契约类 gate 只能拒、不能补，可能让模型反复重试 | 拒绝理由必须写明修法；同一 gate 连续拒绝 N 次后转入待裁队列 |
| 「一句话 + 选项」造成信息损失，秘书出题偏差 | 附言永远可用，文件和证据一点即达；被否决或改写的选项计入指标 |
| 前端素材工作量拉长周期 | 前端作为支线，不阻塞主线；F1 样张不过不往下做 |
| 默认面板或侧栏控制不可行 | 阶段 0 第 5 项先验；不可行就退到「侧栏入口 + 主区域面板」，仍保持信息分层 |
| 重蹈旧仓臃肿 | 开发规范设比例上限；量不出收益的机制降级或删除 |

## 8. 约束与边界

**第一阶段不做**：
- 飞书和其他外部通道（后置）；7×24 服务器形态与手机端（后置）
- 多工作区、多房间、程序生成房间、房间编辑器、昼夜变化、庭院（前端 v2/v3）
- 九级晋升梯、判决模型、RSI 自动提案（只建人工标注台账，攒数据）
- 沉淀作者面、沉淀包格式、公开画廊
- 主动巡逻、对外动作（发版、社区回复）、成本预算、DR
- 记忆的 M2–M6 分层、派生检索索引、embedding
- teammate 级 worktree 隔离（模型侧工具不能指定 cwd，后置）

**硬约束**：
- 秘书永不执行；查文件、排障也派 worker
- 只有两类真相；派生态和前端永不回写
- 硬闸只放在 pre-execute；不挂 `fs/*-intent` 单槽钩子
- 不修改官方插件行；只 insert 自己的行
- 凭据不进聊天和普通文件
- 汇报完成必须有独立证据
- 首期写死单用户

**与设计包原执行队列的关系**：原队列的「规范起草六步 + 三 spike + 评估器补救」按本 PRD 改为按阶段、按需推进。事件脊 schema 收窄为 v0（阶段 1）；评估器九级梯延后，等阶段 5 攒到真实拦截台账再做；三个 spike 中，「teammate worktree cwd」已由源码分析基本回答为否（模型路径），另两个并入阶段 0。
