# 项目缘起与想法演变

> 读者：接手本项目的 Claude Code。这份不是规范，是**来历**：老板（陈展昕 / CovD831）最初想要什么、旧项目怎么长起来的、他的想法在 2026-11-21 至 11-22 的设计期里转过哪几次弯以及为什么。
> 读法：简报（NEW-REPO-BRIEF）告诉你现在定的是什么；这份告诉你**他是怎么想的**。两者冲突时以简报为准，但遇到简报没写到的空白，用这份里的思路去填，不要用通用做法去填。
> 内容来源：老板在这两天对话中的亲述与裁决、旧仓审计、秘书侧记忆。日期均为 2026 年、北京时间。

---

## 1. 缘起：旧项目是什么

旧仓 **CovD831/dsh-agent-teams**，是老板 fork 自 NanmiCoder 的同名项目 —— 一个跑在 DeepSeek Harness (DSH) 上的 AgentTeams 插件。fork 之后：

- **编排层他基本没动**，沿用原项目的 team 编排；
- **他自己的原创工作是「判局层」**：在 agent 生命周期的关键位置决定何时、何处触发哪些检查 —— 准入、契约、派发、完成、交付、运行时六类插入点，外加一个**注册表**（旧仓 `src/gates/registry.ts`），让每个判局（gate）成为可插拔模块，而不是写死在流程里的 if；
- 本地改动长期没有回传公开仓，公开仓只是大致同构，本地为准。

这个项目对他不是练手：判局层是他对「agent 团队为什么会失控」这个问题的回答 —— 编排谁都会写，难的是在对的时刻做对的检查，而且检查本身要能沉淀、能复用、能被评测。

## 2. 他最初想要的四件事（2026-11-21 02:11 亲述）

设计期第一晚，他把愿景完整说了一遍，四条主线从未变过，后面所有裁决都是它们的展开：

1. **人人可沉淀工作流**：往系统里加判局，本质是把一个人的开发习惯和流程「存」进来。目标是任何人都能轻易沉淀，不只是他自己 —— 这是产品的立身之本，不是功能之一。
2. **模块评测 + RSI**：每个模块要按它带来的后续收益被评判 —— 收敛性、稳定性、缺陷率、值不值得留、怎么优化。他对机制的一贯标准（2026-11-13 就定下）：**机制必须证明有稳定的收敛收益才配留下**，先测单项、再测组合。
3. **Personal Agent / 秘书**：单一入口、对注意力友好；秘书负责对话并指挥跨项目跨工作区的 agent 团队；形态以 bot 为佳（类 Grok bot），部署在服务器上常在线。他当时就点了参考系：DeepSeek SuperAgent 及其二开、开源 personal agent 生态。
4. **上报即缺陷信号**：每一次上报（escalation）都意味着某条规则有缺陷，是系统自进化的信号；上报之所以需要人裁，只是因为判据不足。目标：**越用越少打扰**。

前端的想法同一晚也定了形：像素游戏风、小人对应 agent 状态、用预定义状态类别表达；信息分层 —— 默认看小人和状态，点开是中密度，最深层是原始 AI 客户端（类 Codex）。初衷有二：对外宣传，以及缓解「看不见子代理在干什么」的焦虑。

## 3. 旧仓的发展与终点

- 判局层长到了 **15 个 gate**；与此同时 DSH 官方在版本迭代中把他做过的很多工具**内化或重做**了。设计期做的官方能力审计结论：15 个 gate 中 **13 个仍然独有、2 个部分重叠、0 个被官方取代** —— 判局层没过时，过时的是他自维护编排与工具层的必要性。
- 旧仓的问题他自己的定性（02:22）：**「很臃肿，很乱」**。本地改动与公开仓脱节、结构随功能生长而失序。
- 结论：**开新仓**。不是推倒判局层 —— 判局层是资产，要带走；推倒的是仓库的组织方式。新仓的规矩先行：**架构和开发规范先立，再写代码**（这一条在新仓脚手架阶段必须遵守，别先写功能后补规范）。

## 4. 想法转变（按时间，每次都附他为什么改）

### 4.1 底座：从自家 fork 换到官方 agent-team（03:09 裁定）
原计划是在旧有编排上继续长。审计摆出事实后他改了主意：「我们原本做的很多 tool 其实都被官方内化或者做了。」—— 维护一套与官方重复的编排是持续税，判局层挂到官方 team 上反而干净。**教训形状：他对沉没成本无感，证据到了就换路线。**

### 4.2 秘书：从「小事自己答」到「永不执行」（02:22 纠正，全项目最重要的一次纠正）
秘书侧最初的设计是三级分流：小事秘书自己答、中事派 solo、大事拉 team。他当场否掉：**哪怕最简单的代码，秘书也不许自己写，一律派子 agent**。理由：秘书的命是「时刻能回应」—— 她一下场干活，入口就堵死，整个形态就不成立。所以秘书的工具面是**零执行工具**（连只读 shell 都没有），只有永不排队的结构化状态查询特权槽；查文件、排障都算执行，派诊断 worker 去。solo/team 的分工只存在于执行层内部，与秘书无关。

### 4.3 Lead：不另设一层（03:18）
参考 louifinn 二开的三级结构后定的折中：不新建 Lead 层，**每个工作区的主会话兼任 Lead**（需要团队时它是官方 team 的 Lead，否则直接派 solo worker，全系统三级）。但 louifinn 的纪律全抄：写在交付前、幂等键、Lead 只有提议权、每项目并发上限。

### 4.4 旗舰场景具体化 + Magpie 指认纠正（03:22 / 03:25）
他把第一需求说死：系统建好后先干的不是泛泛写代码，而是**维护他的开源项目 —— 处理 issue、处理 PR、审查、开发**。参照物他点了「magpie」，秘书侧先入为主查了 apache/magpie 和插件生态，他纠正：是 **yetone/magpie** —— 一个开发基本由 AI 跑、迭代极快的模型路由项目，yetone 公开分享过自己的工作流。这个纠正改变了调研的整个取样：要学的不是某个工具，是**一个人 + AI 团队真实维护一个高流量开源项目的运转方式**（后来实测：issue 侧才是瓶颈，注意力分配而非清空队列成了旗舰的目标函数）。

### 4.5 沉淀：从单通道到双通道（03:35）
他补了一层：沉淀不只是「用户把自己的工作流存进来、系统帮他优化」，系统还要**从真实摩擦里自己长出候选模块、向用户提议、由用户选择是否装** —— 提议权在系统，决定权在人，永不自动安装。同日连带定下：**红绿测试是一种可沉淀的判局类型**（修复必须带「无修复即红」的测试 —— 这是他的开发习惯，要做成用户可存的类型而不是写死）；**投影律**（一切派生状态与前端 UI 都是只读投影，永不回写）。

### 4.6 RSI 的定位：评估器才是核心（03:42）
秘书侧一度把「根据真实摩擦做提案」当作 RSI 的主轴。他纠正：那只是 RSI 的一部分；**评估器才是核心 —— 先能评估收益，迭代才有依据**。yetone 的「同一课出现三次就升为硬规矩」在他看来只是 RSI 里很基础的一个判局（后来的作者面设计甚至发现：按原话存这条会违反九级晋升梯，需要「宪法纠正」环节）。他还给了一条方法论：**模型层（架构与训练）的思想会系统性地迁移到 agent 应用层**，新仓设计要主动做这张映射表（后来成文 26 个概念，11 个是机械性真迁移）。

### 4.7 判决模型：从「不引入」到「开源自托管、按域适配」（04:25）
SAG 调研的初步结论写了「JEV 不引入」，他纠正：不引入的只是 TypeSafe 的托管闭源服务；**判决模型这个品类他本来就打算引入**，用开源版本，且必须按域适配 —— 至少做阈值/数值标定，有数据后微调。他的选址判据：**哪里数据大量产生、且自动标签随之而来，判决模型就该坐在哪里** —— agent 团队恰好两条都满足（执行产数据、任务成败即天然标签），问题只是每个裁判坐哪。最终落成：原则已批（权威 ∝ 标签质量 × 可逆性 ÷ 错误成本；影子→顾问→软分→有限硬权四级授权），**12 个位置的放置图至今仍是提案状态、未批** —— 施工时不要把放置图当裁决。

### 4.8 记忆：权重的三级跳（03:57 → 22:57）
记忆是这两天里升格最陡的一条线，轨迹本身就是他思路的样本：
- 起初它只是 13 个原子点里的一个点（点 11），秘书侧一度想缓办；
- 他点名要深研（「秘书需要很好的记忆管理」，并推了 Linger），记忆升为单独一轮；
- 逐点审计（他下令的，见 4.9）判记忆仍然 UNDERWEIGHTED，且点破：之前的点位权重是按「借件好不好借」排的，不是按「这个点坏了会怎样」排的，而记忆的失败模式全是静默的；
- 酒馆（SillyTavern）调研回来后（确定性注入引擎 + 表格治理面），他定调（22:57）：**「记忆系统是非常重要的，前端想做得像游戏、秘书这个角色要有真实感、高效，都跟记忆分不开」** —— 记忆从后端件升为产品体感本身：真实感 = 连续性，连续性只能由记忆提供；假记忆比没记忆更伤真实感，所以出处/tombstone/取代链是产品要求不是工程洁癖。
- 落点：记忆与事件脊同列第一梯队；真实感立三指标（重复提问率、假回忆事件数、被纠正记忆条数/周）进 RSI 台账。

### 4.9 对自己方案的审计文化（04:42 下令，04:48–05:03 收官）
他主动要求对已拆的原子点逐点派子代理审计、并查漏点 —— 审计判了 11 个 UNDERWEIGHTED、2 个 MISSING、1 个 STALE、**0 个 SOLID**，还查出三件记账事故：一条「已裁决」（首通道）其实从未真裁、一条是打包囫囵批的、一条把提案记成了定案。他当场补裁（飞书第一、个微挂起待风险评估）、打包确认、降级标注。审计还挖出六个整类缺失的点（事件脊/安全/对外动作/恢复/成本/巡逻），他全数立项（16:00「这几个都立」）。**这是他的工作方式：方案形成后先自我攻击，再进入执行；「已决定」必须经得起回查。**

### 4.10 通道与范围的收敛（05:01）
首通道在「飞书 vs 个人微信」之间悬了很久才真裁：**飞书第一**；个人微信挂起，先做封号/协议风险评估再说；手机端后置，先打地基。首期范围写死单用户。这些收敛都不是技术偏好，是风险与注意力的排序。

## 5. 他评判方案的方式（施工时按这个标准自检）

- **先问哪儿最容易坏、坏了什么样**：权重按失败代价排，不按实现难度排；静默失败（假保证、毒化看板、无声漂移）是最坏的一类。
- **机制要证明收敛收益**：任何「聪明设计」都要能被评估器量出收益，量不出就降级或删；频率只配提议，裁决归评估器。
- **真实摩擦 > 想象需求**：候选改进从真实运行的摩擦里挖，不从「将来可能需要」里编。
- **记账必须诚实**：提案不能记成定案、打包批要逐项可回查、自报完成不算数（汇报前要有独立证据）—— 这三条在设计期都真实触发过纠正。
- **判断先行**：要结论和取舍，不要选项菜单；证据到了就换路线，不恋沉没成本。
- **生产流保护高于一切**（他在并行运营的 agent2api 生意上的一贯纪律，本项目同样适用）：蓝绿、无感切换、单写者；有断流风险就停下来报，不硬干。
