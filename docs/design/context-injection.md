## 1. aoci 是什么

**确认存在**：GitHub 组织 `aoci-spec`，仓库 `aoci-spec/aoci-code`（Go，2,897★ / 268 fork，建于 2026-08-08，
最近 push 2026-11-21，v0.2.0-rc3，默认分支 main，官网 aoci.ai）。`aoci-spec` 是组织名，**没有**独立 spec 仓库，
规范在仓库 `spec/public/` 下。组织另两个仓库：`aoci-agent-releases`（cognition-first 编码 agent 发布包）、
`aoci-sweqa-r5`（评测复现包）。许可 **FSL-1.1-MIT**（源码可得，非 OSI 开源；MIT 于各版本发布两周年生效，
含 Permitted Purpose 限制）。

**它是什么**：AOCI = AI-Oriented Cognition Infrastructure，方法+协议层；AOCI-CODE 是 `aoci` CLI + MCP server
（9 个工具）+ 索引。做法是把「理解整个系统」压成一份**模型写的、纯文本、git 版本化的索引**，agent 开任务前
先读它，替代逐次搜索重读。

**符号体系**：每个受管对象一行 **FRAS**：`F` 职责 / `R` 必须一起读的强关联 / `A` 对外接口契约 /
`S` 非显而易见且不能搞错的约束；行首标签 `[A+B+C+D+E]` 标层/域/重要性/特征/规模，字典写在 `aoci.meta.txt`。
程序只校验字典与结构，**不裁决语义**。压缩对象是**代码仓库（含配置/测试等受管对象）+ 数据库表结构**，
不是对话、不是需求/规范文档。**未找到**针对规范文本或对话历史的压缩方案。

**解码由谁做**：模型直接读。MCP `aoci_overview` 分块投递（`chunk_tokens` 默认 7000，范围 4000–24000），
`next_cursor` 翻完才算交付；标签含义由 Meta 字典解释，程序不做语义展开。写入走 Agent-native：宿主模型读源码
逐条写，预算默认 200k target / 300k warning / 400k max token，S 字段有字符配额（如 C9-8 ≤600、C7-4 ≤200），
代码稳定后增量维护并做 drift/CAS/恢复。中文：locale 只有 en-US / zh-CN，只控制 CLI 帮助、guide、AGENTS 模板
与配额键；**条目按写时语言保留，同一仓库可中英混存**。

**实测数据**：唯一公开实测是 `aoci-sweqa-r5`（CC-BY-4.0，15 个 Python 仓库 × 三臂 × k=10，答问模型
**DeepSeek-V4.1-Flash**（thinking 关），判分 Claude Sonnet 4.5 五维 0–100）：
- AOCI − 裸 = **+1.36**（p<0.0001，11/15 同向）；AOCI − CodeGraph +0.22（p=0.21，分不开）；CodeGraph − 裸 +1.14。
- 读源文件更少，**20–40% 题不打开任何源文件**；答案长 1.3–1.5 倍。
- 索引越大增益越小：≥6 块时仅 +0.55（p=0.29）；4 仓为负（pylint −2.12、requests −1.90、reflex −0.44、streamlink −0.50）。
- 认知轮 attestation 提交率 100%，但该模型**几乎不通过** AOCI 自己的 attestation 挑战 → 协议是投递机制，不等于理解。
- 输入 token 暴涨（sympy 臂 1.97M vs 裸 57K，大部分命中缓存）。
**未找到**：独立论文/技术报告；针对 kimi 等中档中文模型的实测；索引对「实现类任务」成功率的实测（SWE-QA 是答问类）。

**优点（事实）**：跨会话/跨 agent 复用、可 diff/审查/回滚、漂移检测与受控更新、只写一份全局语义先验。
**缺点（事实）**：首次建索引约每 20 万行 1 小时；需宿主支持 MCP 且要重启；FSL-1.1 非开源。

**评估**
- 对中档中文模型（kimi、deepseek flash）**可能增加误读**（推断，但有实测支撑）：S 字段配额与标签字典是额外
  符号负担，同档模型实测增益已缩到 +1.36 且有 4 仓为负、「what」类题 −0.39，说明索引把「找文件」换成了「读精炼
  摘要」，模型照抄摘要而不核原文的风险真实存在。风险最高处是 S 字段（约定俗成、无法从代码推出的约束），
  恰好也是它声称最有价值的部分。
- **压缩后人类可审查**：可以。索引是仓库内 git 文本，可 diff、可 review、可回滚；但官方 FAQ 明示 all-green
  **不证明语义正确**，条目需对照源码/schema/测试由人审。

## 2. 旧仓与设计包的已有探索

  只注入【契约 + 相关读数】**；链条连续性必须放在外部（契约=`team.json` 的 objective/acceptance/inScope/verify，
  台账=status/output/attempt，判决=`.agent-teams/judgements/`）；交接有固定格式，**只交事实与读数、不交推理过程**

## 3. 方案对比

| 方案 | 省多少探索 | 写入成本 | 出错风险 | 可审查性 | 适用于秘书派活 |
|---|---|---|---|---|---|
| 队长精炼任务卡（每任务 ≤15 行目标/接口/约束/验收） | 中高（砍掉盲目搜索与重复读） | 中（每卡 2–5 分钟，队长出） | 低（队长在主上下文有原文，可核） | 高（卡即文本，可审可改） | **是（首选）** |
| 模块胶囊（每模块 ≤15 行接口+约束+坑，持久化随模块更新） | 高（跨任务复用） | 中高（建一次、维护易漂移） | 中（索引过时比原文误读更隐蔽） | 高（git 文本、可 diff） | 是，但只对稳定模块、需漂移检测 |
| 符号压缩（AOCI 式 FRAS 一行一条） | 高（一次读全貌） | 高（首建约 20 万行/小时 + 治理） | 中高（中档模型实测有负收益；S 字段照抄风险） | 高（纯文本可审，但语义需人核） | 暂不（成本与收益不对等） |
| 继承上下文分身（fork 主会话上下文/同窗口继续） | 高（不探索） | 极低（自动） | 高（过期结论与本轮事实并存，旧仓已实测踩坑） | 低（上下文不可 diff、不可审） | 否（与「worker 可弃、状态在文件」相悖） |
| 只给路径清单 + 按需检索（现状） | 无（省的是队长） | 极低 | 低 | 高（原文即审） | 是，但探索成本全部转嫁给子代理 |

## 4. 建议

**开发流程（现在就做，2 条）**
1. 把 `~/Desktop/dsh-secretary/docs/AGENTS-WORKFLOW.md` 任务卡的「背景必读」从**列文件绝对路径**升级为
   **队长先产出的精炼块**：每项 = 一句话职责 + 关键接口/命令 + 必须复用的模块 + 已知坑 + 原文路径；
   子代理先读精炼块，再按需读原文，**冲突时以原文为准**并交回异常。这是旧仓 DISPATCH-RULES「契约 + 读数」
   的现成做法，不改派工结构。
2. 任务卡加**注入预算与硬报错**：背景必读 ≤40 行 / 文件引用 ≤5 个，超限由队长压缩或拆卡，**不静默截断**
   （抄注入封顶纪律）；任务卡模板显式写「路径为引用，内容以原文为准」。

**产品（secretary_dispatch 注入给工作区的上下文包，将来）**
- 采用「**契约卡 + 按任务范围生成的模块胶囊 + 原文路径索引**」三层：秘书不产出转述，只产出指认（路径、行、
  命令）与按任务范围裁剪的胶囊；每条胶囊带出处与更新时间、可展开原文；总注入预算硬封顶、超限报错。
  不做整仓符号索引；不做继承上下文分身（旧仓已实测其失败模式）。

**若要试 aoci，最小实验设计**
- 对照：A 现有任务卡+自行读全文；B 任务卡+队长精炼胶囊；C 任务卡+AOCI 式一行一条符号索引（主模型预先产出、
  git 版本化、只针对目标模块而非整仓）。
- 任务集：同一项目 20–30 张真实任务卡（探索 / 实现 / 机械执行各三分之一），验收命令固定。
- 指标：首次动作前读文件数与探索 token、验收一次通过率、返工率、交回证据完整率、队长验收耗时、总成本；
  另记「照抄索引而不核原文」的纠偏次数（误读指标）。
- 控制：同档模型（kimi、deepseek flash 各一组）、同一宿主、每臂 ≥3 次重复；先跑 5 张卡校准预算与分块再全量。
- 判据：C 的探索 token 显著低于 A **且**验收率/误读不劣化才引入；否则保留 B。
